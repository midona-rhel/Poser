# Contributing

Work is tracked as GitHub issues and lands through reviewed pull requests. [AGENTS.md](AGENTS.md) has the rules for writing and for what to check before handing work in. They apply to people and AI agents alike.

## 1. Start from an issue

Every change starts as an issue, made from the issue template.

- Start with what goes wrong for the person using the program, then what should happen. End with how to check it.
- Link the code that shows the problem, as a link to a published commit and its lines. Say in a few words what the reader will find there.
- Say whether something was seen in the running program, read in the code, or is a guess.
- Give the steps to see it: where to start, what to press, and what should be seen.
- Search for related issues first and link them instead of repeating them.

## 2. Branch

Name a branch after what it is for: `feature/`, `bug/`, `ui/`, `perf/`, `refactor/`, `docs/`, `test/`, `chore/`, `deps/` or `release/`, followed by a few words, such as `bug/undo-after-reset`. Keep one issue per branch.

## 3. Commit

- The first line says in plain words what changed, with the issue number in brackets when there is one. No `fix:` or `docs:` prefixes.
- One change per commit.
- Commits are made in the maintainer's name. AI tools are not authors: no AI author names, no `Co-Authored-By` lines for them, no "generated by" lines and no links to AI sessions.

## 4. Open a pull request

- Fill in every section of the pull request template: what goes wrong, what the change does, how it was checked, and how to try it.
- Say what was tried in the running program, what was only built or read in the code, and what was not tried.
- Report results as sentences a person can follow. Leave out line counts, model names and the story of the work.
- Review the whole diff yourself before asking for a review. For a clean-up, name the code you deleted.
- Answer and resolve every review comment before merging.
- Merge with squash, so each pull request is one commit. Merge only when the maintainer asks for it.

## 5. Code

- **One way to do each thing.** Before writing something, look for the code that already does it and use that. When two pieces of code do the same job, keep one and delete the other. Delete what a change replaces in the same change.
- **Names.** A name says what the thing is in plain words.
- **Checks.** Only check for something that can really happen and that matters when it does. Before keeping a check, find the action that leads to it. Do not guard against things a person cannot do, do not catch errors around code that does not throw, and do not write a fallback for a value that is always there. Keep checks for things outside the program's control, such as a missing file.
- **Comments.** A comment says why the code is there, in a plain sentence. Do not write a comment that repeats the code, tells the story of a change, or needs another file open to make sense.
- **Tests.** Add a test only when it protects behaviour someone depends on. A different correct implementation must still pass it. More tests is not better coverage.

## 6. Documentation

- Each thing is explained in one place. Other pages link to it.
- Write down what is true and worth knowing. Do not write a page per class or module.
- Plans, audits, notes and records of what was tested do not go in the repository. Work is tracked in issues; what was tested goes in the pull request.
- Delete text that is no longer true. Git keeps the history.
- Check every statement about what the program does before writing it.
- Write each paragraph and each list item on one line. The editor wraps it.

## 7. Release

A release is built from its own `release/<version>` branch. The steps are in [the release runbook](docs/release/runbook.md).

Release notes are for people who use the program. Each bullet says what they will notice, as a plain statement about the program. Name what the person ran into or can now do, not how it was fixed. Do not start bullets with Added, Fixed or Made, and do not address the reader as "you". Leave out changes nobody would notice. Put what people will care about most first, grouped under headings by area. Give the release a title that names what changed, plainly.

## Project specifics

- Work is merged into `main`. Issues use the [issue template](.github/ISSUE_TEMPLATE/work_item.md) and pull requests the [pull request template](.github/PULL_REQUEST_TEMPLATE.md). Give each issue one priority label; P2 is the usual one.
- Build and test with `dotnet build Poser.slnx -c Release` and `dotnet test Poser.slnx -c Release --no-build`. How to try a change in the game is in [testing](docs/process/testing.md), and the limits on unit tests are in its [test budget](docs/process/testing.md#unit-test-budget-and-relevance).
- The pages under `docs/features` are for people who use Poser and walk through the interface in the order a person meets it. The pages under `docs/architecture` and `docs/process` are for people who change it. [docs/README.md](docs/README.md) lists them.
- The release steps are in [the release runbook](docs/release/runbook.md).
